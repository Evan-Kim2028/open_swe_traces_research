# Hidden test verification — authored_batch3/goa (VFbatch3goae)

2026-09-21 — black-box hidden suites for the goa `expr` units of
`authored_batch3`, plus `_author/contract.md` for every verified unit so the
cohort can be staged (`stage_units.py` reads contract.md unconditionally).

`gold.patch` was never opened. Every assertion is graded against
`_author/DETAILS.md` commitments, `api.md`, and exported black-box behaviour
only.

Provenance note: the suites, runners, contracts, and the two `_tools` scripts
were seeded from sibling worktree `oswt-VFbatch3goad`, whose `_author` inputs
(excluding contract.md) are byte-identical to this worktree's for all 12 usable
units. Each suite was then re-audited here line-by-line against DETAILS, four
assertions that pinned undisclosed phrasing were weakened to shape (see
"Deviations from the seed" below), all runners were regenerated, and every
Docker gate was re-run locally — results in `outputs/VFbatch3goae.log`.

## Method

- Suites live at `tests/hidden/expr/<unit>_bb_test.go`, all `package
  expr_test`, exported API only, one `TestDetailNN` per DETAILS line — the
  numbering traces a failure back to a commitment.
- Fixtures are hand-built `expr` trees; where lifecycle code needs a bound
  design the fixture registers services on a fresh `RootExpr` and calls
  `root.WalkSets` (the same binding the DSL produces), then drives
  `Prepare`/`Validate`/`Finalize` at the level production code uses.
- `tests/test.sh` per unit is generated by
  `experiments/pipeline/authored_batch3/_tools/gen_test_sh.sh`:
  sha256-guarded hidden-file install into `/app`, then
  `go test -count=1 -timeout 15m -run '^(TestDetailNN|...)$' ./expr/...`,
  reward at `/logs/verifier/reward.txt`.
- Docker gates via `_tools/verify_goa.sh` in `ladder-base:goa` with
  `--network=none`: excised+hidden must FAIL, +gold must PASS, +cheat must
  FAIL, and neither gold nor cheat may touch a `*_test.go` or `tests/` path
  (A12, checked by patch-path scan — every patch touches exactly one non-test
  source file).
- Contract coverage was checked mechanically: every unit's contract names each
  `TestDetailNN` exactly once and no contract row lacks a test (1:1 in all 12
  units).

## `Inferable: no` assertion policy

`no` rows assert shape, never the literal: an error exists and names the
offending field/type/kind/scope (the name is a fixture input, so the solver
cannot fail on guessing it); or a relational outcome holds (pointer identity,
set membership, ordering of identifiable markers, dedup counts, precedence
winners, exact error cardinality). Exact message prose is never pinned unless
DETAILS itself quotes the literal AND the contract row discloses it. Examples:

- `attachsvc` D3/D4/D6/D7: asserted via set membership, attribute-vs-type
  identity, per-transport root equality, and ordering of named markers.
- `defval` D2/D5/D7/D8/D10/D11/D12: each nesting context surfaces an error
  naming the offending position (label literals unpinned); numeric bounds via
  accept/reject at the committed limits; enum/union/map rules via
  accept-reject matrices and deterministic-order via sorted marker names.
- `grpcend` D2/D3/D5/D6/D7/D10/D11/D12/D14: error-policy resolution via
  service-then-API precedence and duplication (not sharing); stream-compat via
  enable/disable per level and shadowing; union dedup asserted as exactly one
  validation error; scalar-payload mapping asserted as "rejected when not
  exactly one compatible field"; security-tag movement asserted via metadata
  membership, committed `"authorization"` mapping, and requiredness
  propagation.
- `httperrexpr` D7/D9: non-object header rules via accept/reject counts
  (>1 rejected, exactly 1 accepted); finalize precedence via the reachable
  identifier path.
- `httpresp` D3/D7/D8/D9/D10/D11/D13: the status boundary set is the committed
  boundary itself (disclosed in the contract); header/cookie multiplicity via
  count thresholds; generated wrapper naming via the committed
  `<Service><Endpoint>ResponseBody` shape; `apikit-attribute` mapping via
  prefix containment plus skipped/requiredness relations.
- `httpsvc` D2/D4/D5/D6: path joining asserted arithmetically on fixture
  paths; JSON-RPC detection via meta flag toggling; route defaults via the
  committed POST verb and shared-path relations.
- `methodval` D5/D6/D7/D8/D10/D11/D12: scope/tag rules via accept-reject with
  per-kind alternative name sets; unwrap rule via named-type fixtures;
  finalize defaults via non-nil checks; inheritance via pointer-non-identity.
- `resultview` D1/D3/D5/D6/D8/D9/D10/D11/D12/D13: canonicalization via
  round-trip on fixture identifiers; origin via earliest-declaration identity;
  memoization via pointer reuse; collection naming via the disclosed
  `"Collection"` suffix; view plumbing via projected identifier membership.
- `rootval` D3/D5/D7/D8/D9/D12: ordering via named markers; dedup via error
  counts; shared-route detection via trigger/no-trigger matrix; relocated-type
  rules via dependency-path notation (`a.b`, `[]`, `[key]`/`[value]`), fix-hint
  prose unpinned.
- `secschemes` D1/D2/D3/D6/D8/D9/D12: name mapping via membership in the
  disclosed spelling set; panic-on-unknown-kind via recover; flow URL coverage
  order-free; copy semantics via shared-vs-deep pointer checks; hash via
  sensitivity to each joined field (join format unpinned).
- `svcerrors` D3/D4/D6/D7/D8: generated-constructor detection via type
  provenance; consistency via per-position matching; finalize markers via
  presence/absence; origin reuse via pointer identity.
- `svcexpr` D1/D2/D3/D5/D8/D9/D10: scheme prefix order via parse outcomes;
  wildcard naming via fixture-parameter names; URI resolution via substituted
  fixture URI; localhost defaults asserted by scheme and reuse — the port
  literals themselves are not pinned.

## Deviations from the seed (this worktree's audit findings)

Four assertions in the seeded suites pinned phrasing a solver cannot derive;
each was weakened to shape, `test.sh` regenerated, and the unit re-verified:

- `grpcend` D6: counted the phrase `"array elements"` in an error string.
  Replaced with `len(verr.Errors) == 1` — the committed behaviour is that the
  shared union is reported *once*; cardinality is the honest shape.
- `grpcend` D7: required `"1 field"` in the error text. Replaced with
  error-exists — a solver may phrase the count differently ("exactly one",
  "more than one field").
- `httperrexpr` D7: required `"more than one"`. DETAILS quotes the literal,
  but the contract row states only the constraint ("at most one header"), so
  the phrasing is not derivable at L2. Replaced with error-exists; the
  single-header acceptance case is still asserted separately.
- `httpsvc` D9: required `"does not match"`, which appears nowhere in
  solver-visible material. Replaced with error-exists plus naming the
  offending error `"ghost"` (a fixture input — verified against gold that the
  diagnostic does name it).

All other literal-looking assertions were audited and are legitimate:
committed literals quoted in DETAILS *and* disclosed in the contract (eval
names like `"unnamed service"`, `"HTTP error "`, `"Server "+name`, hash
formats like `"_service_+<name>"`, the `"API"` fallback name, the
`"Collection"` suffix, `apikit-attribute` prefix, `"at least one URI"`,
`host "name"` prefix); fixture-echo round-trips (input names/values must
propagate); alternative sets (`"API key"|"apikey"|"api key"|"key"`);
domain concept words (`"primitive"`, `"canonical"`, `"POST"`, `"rpc:tag"`,
`"authorization"`); and absence-checks (`!Contains`) that are weak-not-unfair.

## Refused / weakened assertions

- `httpresp` D12 `Tag`: DETAILS lists `Tag` among the scalar fields `Dup`
  copies; the observed behaviour does not copy it. Tag is asserted neither
  way — the contract row lists the copied fields and the DETAILS mismatch is
  flagged here rather than bent.
- `methodval` D9: the merged interceptor set is not observable as state after
  `Prepare`/`Finalize`; it is asserted through `Validate` diagnostics (the
  merged set is what interceptor validation checks), which is the behaviour
  DETAILS commits to.
- `resultview` D11 negative case (non-result-type collection element):
  rejected by panic rather than by returned error, so the assertion is
  "rejected (error or panic)" — the contract states the rejection
  requirement, not a mechanism.
- `httperrexpr` D9: the result-type-identifier content-type path is only
  reachable when the body keeps result-type identity (non-object result
  type); the fixture uses that path and asserts the identifier wins while an
  explicit response content type is preserved.
- `grpcend` D4/D5: two negative checks assert a *phrase* is absent
  (`"cannot define both"`, `"requires the method"`). These are conservative —
  they can only pass a buggy implementation that words its error differently,
  never fail a correct one — so they were kept rather than tightened to
  `txt == ""`, which could false-fail on unrelated validation noise in those
  scenarios.

## Fixture notes (reusable)

- `Validate()` returns a non-nil zero-length `*ValidationErrors` on success —
  assert on `len(err.Errors)`/message text, never `err != nil`.
- `AttributeExpr.IsRequired` delegates to the *user type's* attribute when
  `Type` is a `UserType` — requiredness fixtures must set `Validation` on the
  user type's own attribute, not the wrapper.
- `GRPCErrorExpr`/`HTTPErrorExpr` mappings must carry a prepared `Response`
  (non-nil `Message`/`Headers`/`Trailers`/`Cookies`) before `Prepare` may
  duplicate them.
- `HTTPResponseExpr.Finalize` does not compute the body — bodies are assigned
  by endpoint-level `Finalize`; error-attribute remapping only runs for
  `ErrorResult` bodies that are nil/empty or carry `origin:attribute` meta.
