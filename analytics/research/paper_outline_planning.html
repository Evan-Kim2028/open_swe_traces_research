STAGE 1 · GO

Building a Synthetic SWE Factory, Stage 1: Go

Every certified task carries a prompt that fails and a prompt that passes. Difficulty is the gap between them.

We cut working behavior out of nine real Go projects and write the tests without ever seeing the solution. A task is kept only when one model fails it from a bug report and passes it from a full description. That pair is a per-task difficulty certificate, and it is made of information rather than of code.

1The gap

What a generated coding task needs, and who already builds them.

1.1 A task has to be checkable and fair

People who train coding agents need tasks with a real check. Mined GitHub issues bring their own tests and whatever difficulty the issue happened to have. A generated task can do better when two things hold. The tests check the behavior that was removed. The prompt gives a programmer enough to rebuild it.

1.2 The pipelines already in the field

SWE-bench and SWE-Gym start from real issues and the tests already in the repository. SWE-Gym showed that a few hundred expert traces lift a 32B model about 14 points on SWE-bench Verified. SWE-smith injects bugs so those existing tests fail, and scales that to about 50,000 Python tasks. R2E-Gym builds about 8,000 tasks from commits and writes tests for them. ProgramDistill turns 26 web apps into about 4,000 restore-the-behavior tasks, and sets difficulty by how many behaviors the agent must restore together.

CodeMidas (Ye et al., 2026) is the closest construction. It takes source code as its only task input, across 23 languages, and keeps 5,545 training tasks. An agent removes implemented behavior, writes a behavioral statement, and builds tests by running the original code and recording what it returns. One statement goes to the solver. Tasks that a screening model always passes, or always fails, leave the training pool.

1.3 Where this factory sits

We take the input CodeMidas takes, source code and nothing else, and change two things.

The wall. Our test author sees the list of behavioral commitments, the public API, and the repository after the cut. It never sees the removed code. CodeMidas builds its tests by running the original and recording what it returns, so its tests are derived from the answer. Ours are derived from a specification of the answer, which is the only version of the test that can be wrong in a way worth catching.

The certificate. Every other pipeline in Table 1 decides difficulty by whether some model failed. That conflates two different tasks. A model can fail because the work is genuinely hard, or because the prompt never carried enough information to do it at all. One prompt cannot tell those apart. We give the solver two prompts on the same task: a bug report, which must fail, and a full description of every behavior the tests check, which must pass. The failure says the task is hard. The pass says the task was specified well enough to be solvable. The gap between the two is the difficulty dial, and it is the unit of difficulty this factory manufactures.

2The factory

Four steps turn a repository into a certified task.

2.1 Cut the behavior

An author reads a Go repository and removes one self-contained behavior. The public surface stays, so a test can still call it. The removed code is saved as the reference solution. The author also writes a short bug report and a list of behavioral commitments. Each commitment has to be something a solver can derive from material we will show them.

2.2 Write the tests blind

A second agent writes one hidden test per commitment. It sees the commitment list, the public API, and the repository after the cut. It does not see the reference or the bug report. The tests name caller-visible behavior.

2.3 Check the tests against execution

We build the task in Docker. The cut repository fails the suite. Restoring the reference makes the suite pass. A cheat that special-cases the tests fails the suite. A third agent then reads the reference and the tests together and writes the full description, one row per assertion.

2.4 Keep the task when the prompt is the difference

A strong model sees the bug report and fails. The same model sees the full description and passes. We certify that task. The hidden suite is the judge of the code. The two prompts are the judge of the task.

2.5 The cut has to be inside one repository

We tried the obvious alternative and it failed cleanly, which is why this step reads the way it does. Excise a function from a dependency, leave its consumer intact, and grade on the consumer’s behavior. A dependency boundary ought to make the task harder. It does the opposite. 19 of 23 tasks were solved from the bug report alone. A second round targeted only behavior no model could have memorized, obscure project forks with arbitrary but consistent rules, and did marginally worse at 12 of 14.

The mechanism is that the consumer’s call sites are a specification of the dependency. Argument shapes, orderings, and what the consumer asserts afterward hand the solver the contract, so recall never enters into it and making the target unrecallable cannot help. In-repo excision does not have this property, because the excised code’s callers usually go with it. We parked cross-repo construction rather than tuning it. It needs a different construction, not a different selection rule.

2.6 Two axes decide a task

The horizontal axis is what the agent is told. The vertical axis is whether the tests were written without the solution. A certified task sits high on that vertical axis, between the bug report and the full description.

2.7 What each rung adds

L0, bug report. The symptom and how to reproduce it. The implementation is gone.

L1, partial description. One requirement is left out. A test already in the repository covers that requirement.

L2, full description. Prose states every behavior the hidden tests check.

L3, test names. Adds the names of those hidden tests and a one-line description of each.

L4, signatures. Adds the exported function signatures, as stubs.

L5, one test. Adds the body of one hidden test file.

L6, all tests. Adds every test in the tree.

3The dataset

Same method, nine Go projects, 139 certified tasks so far. The run is still going.

3.1 The bug report and the description do different jobs

Of the 299 tasks the pipeline has decided, 131 were solved from the bug report alone and never reached the certificate. 139 failed the bug report and passed the full description. 29 failed both. The screen and the certificate remove about as much as each other, and neither removal is wasted. A task solved from the bug report was never hard. A task that fails the full description was never fair.

3.2 Yield follows the project

Among tasks we could decide, client-go certifies 78% and go-github certifies 14%. The cuts in go-github piled into the same files. Spread the cuts, and the yield moves.

3.3 Nine kinds of Go code

kops and go-git each contribute 25 certified tasks. Messaging contributes 7. The dataset covers Kubernetes operations, version control, API design, storage, the GitHub API, HTTP services, the Kubernetes client, packaging, and messaging.

3.4 How big a reference solution is

The reference patch is the code we removed and can restore. Across the 139 certified tasks, the median change is 127 lines. Most tasks fall between 80 and 320 lines. A quarter of the patches touch two or more files.

3.5 What a task costs to run

Authoring is cheap and trials are not. A unit costs about $1.25 to author. The dataset has spent 2.32B tokens and $519 across 1,239 trial runs, which is 8.3 trials for every certificate against a floor of two, one failure on the bug report and one pass on the full description. 73% of tokens pay for runs past that deciding pair. Gating, meaning refusing a trial whose outcome is already known, is worth about 4× over merely sequencing the trials.

The lesson generalizes past this factory. The expensive part is not generating tasks. It is re-measuring what you already know.

4Scope and next

Stage 1 is Go, nine repositories, in-repo excision, and one solver for 95% of trials. Those are budget choices rather than findings. This is self-funded, so the dataset is deliberately small and deep instead of broad. 527 authored tasks and 1,239 trial runs is enough to show that the construction works and to price what it costs to run. It is not enough to claim that it generalizes, and this write-up does not.

What stage 1 does not claim. That the mechanic transfers past Go; the excision leans on Go’s package and test conventions. That a certificate holds for a model which never took part in screening; too-easy currently means Composer 2.5 solved it. That the ladder is characterized; L1 and L3 through L6 are sparsely sampled, and the dose-response curve is stage 2. A solve rate belongs to the models that produced it, and a certificate does too.

Stage 2 runs the same factory in a second language. The cut, the blind tests, and the certificate stay. A held-out solver screens the dataset.
